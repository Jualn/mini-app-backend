# 业务边界与当前决定

本文只保留仍需开发者遵守的业务决定，按主题维护当前结论，不追加“后文覆盖前文”的阶段记录。不包含接口字段清单、数据库 DDL、测试次数或部署完成声明。
这些决定是对既有需求的整理；修改决定应先明确业务含义，再检查协议和实现依赖。对外协议由 [contracts](../../contracts/README.md) 定义；本文不替代完整契约。

## 活动与公共事项

- 活动与公共事项由运维维护并直接发布，当前不接审核。公共事项继续由 exam 模块承载，不因名称不同新建统一 event 主表。
- Activity 与 PublicEvent 是两个独立业务模型，各自拥有发布/生命周期判断与 Reminder Policy；只共享 Timeline、正文、媒体、Reminder/Notification/Async 基础设施，不建立统一 Event 状态机或按 subjectType 分支的通用业务规则引擎。
- 发布状态、事项阶段、报名状态是不同维度；历史审核状态不能代替公开可见性判断。
- 下架允许修改后重新发布；取消不能恢复。已发布内容保存立即生效。提前结束、取消、下架是不同用例。
- 活动和公共事项共享正文、参与入口、媒体和时间线能力；主体资格由所属业务模块判断。
- Timeline 是 Activity/PublicEvent 的唯一业务时间事实。提醒时刻由各自 Policy 从精确 Timeline 节点与已确认偏移推导；不得恢复主体表历史时间列，也不得把主页公共事项倒计时当成 push Reminder。
- 只有 `PUBLISHED + ACTIVE` 的主体可以产生未来 Reminder；草稿、下架、取消、结束不产生。重新发布基于当前 Timeline 重新计算。Activity 开始提醒采用 T-1h；平台可判定未报名用户的报名截止提醒默认 T-24h。PublicEvent 使用独立 Policy：开始提醒默认 T-1h，具有明确截止语义的节点默认 T-24h。offset 是可调整规则参数，不进入稳定 rule identity。
- 订阅与正式报名独立。activity_enrollment、exam_subscription 表示订阅，不能用其人数消耗正式报名名额；报名也不自动建立订阅。
- Reminder Plan 是否存在不取决于当时有无接收者；到期 fan-out 再解析当前接收者。Activity 开始提醒面向 `SUBSCRIBERS`，报名截止提醒面向 `SUBSCRIBERS_NOT_REGISTERED`；PublicEvent 第一版提醒面向 `SUBSCRIBERS`。订阅与报名仍是独立事实，联合/差集只由 RecipientResolver 按规则计算并按 userId 去重。
- 主页公共事项倒计时以精确的未来 Timeline 节点为候选，订阅仍以事项为单位；每个事项只展示距离当前最近的一个未来节点，该节点到期后重新读取时再推进到后续节点。没有符合条件的 Timeline 节点时不展示倒计时，不回退到主体表历史时间列。
- 人数容量和团队容量区分单位，未知容量不能解释为零名额。开始、结束、报名窗口分别表达含义；待定或仅日期信息不能伪装成精确时刻。

## 提醒与业务通知

- Reminder 表示从业务时间派生的未来意图；取消、时间变更、报名成功等事件型通知不经过 Reminder Plan。哪些事件必须通知需要各业务明确，基础设施不能从状态变化自行推导。
- Activity 第一版主动通知包含取消、影响用户行动的开始/报名截止时间变化、行动地点变化和显式提前结束，接收者为订阅者与有效报名者并集并按 userId 去重；不包含报名成功/取消，也不建立兜底 `ACTIVITY_UPDATED`。
- PublicEvent 第一版主动通知包含取消、影响用户行动的语义时间变化，以及具有真实 location 语义节点的位置变化，接收者为订阅者。当前普通 `END` 状态不能证明“提前结束”，在增加明确的 lifecycle event/reason 前不产生 `PUBLIC_EVENT_ENDED_EARLY`。
- Notification 是每用户的稳定通知内容事实；`IN_APP` 是本地渠道，只有其 Delivery 生效时才进入用户收件箱。外部渠道是否配置、用户是否绑定微信、投递是否成功都不回滚 Notification，也不改变其他渠道结果。
- Notification 创建时冻结标题、正文和必要的渠道无关业务快照，点击目标仍读取主体最新状态。微信 templateId、openid、provider 状态等不是业务通知内容。
- Delivery 是 Notification 的逐渠道派生状态。`IN_APP` 可在本地事务内完成，不创建远程 Job；两个微信渠道各自持久化结果。站内成功不代表微信送达，任一微信失败也不能回滚 Notification 或 `IN_APP`。
- 通知类别第一版为 `ACTIVITY`、`PUBLIC_EVENT`，按 Category × Channel 使用 sparse override；Activity/PublicEvent 普通提醒均为 `USER_CONFIGURABLE`。当前没有确认的 `MANDATORY` NotificationType；未来账号安全类必须通知不得复用或受这两个类别的关闭开关影响。
- 详细的计划、幂等、取消、fan-out、Delivery 与微信边界见 [Reminder、Notification 与 Delivery 设计](reminder-notification.md) 和 [WeChat Integration](wechat-integration.md)。
- 已持久化的开始/截止提醒允许在提醒时刻之后、对应精确业务节点之前恢复；达到该节点后停止新的提醒 fan-out/外部调用，不撤销已有站内事实。普通介绍或附件编辑不创造新提醒意图，不因保存版本增长重复提醒。
- 群体通知第一版按执行时有效订阅/报名关系分批解析，不保存事件时全量接收者快照；执行前新加入者可能收到，已退出者按当前资格排除，当前短批次存在有界竞态。完成后不为新加入者重跑；具体恢复规则见通知文档。固定接收者的评论/回复/资料审核事件保持固定 receiver。
- 主动事件在业务提交时冻结事件身份和变化内容，连续真实变化保留为不同事实，不承诺异步到达顺序。取消/提前结束事件不受 Reminder 的 ACTIVE 限制；消息表达事件时内容，详情反映最新状态。
- IN_APP 关闭只影响未来初始规划，已有消息与阅读状态保持；微信调用前重新检查当前偏好。重复事件不按后来配置补建原来未规划的渠道，重开不触发历史补发。评论/回复/审核等既有设置保持原 owner，不自动并入活动/公共事项六组合。

## 活动个人表单

- 平台个人表单属于活动能力，公共事项当前不支持平台表单。外部报名和无需报名仍是独立参与方式。
- 同一用户与活动保留一条逻辑报名记录；取消后重新提交复用记录。报名有效数与名额约束必须在并发操作下成立。
- 首次提交后冻结表单定义，不能通过取消或作废全部报名解除冻结。
- 答案仅本人及获授权管理员可见，公开表单定义不能包含他人答案。
- 开放受 activity.registration.enabled 控制，默认关闭。关闭时不接受新的平台报名，但保留必要的历史查询、取消和管理能力；实际环境是否开启必须核实。
- 开放前需要真实接口、客户端与数据迁移验收，存在代码和局部测试不等于已经上线。

## 媒体与用户资料

- 存储对象归属由服务端校验，不能仅凭客户端 URL 认定拥有媒体。稳定附件 ID 和 objectKey 分别承担关联身份与存储身份。
- 用户资料的全部指定字段必须完成必要安全检查后原子生效；明确拒绝或检查未完成时保留有效资料，不依赖补偿或后台自动生效。新旧写入口共享此保证，迟到审核不得改写资料。保存返回最终服务端资料；公开昵称允许重复，运营标志来自内部身份事实。协议以 [User/Profile contract](../../contracts/docs/coordination/user-profile-homepage.md) 为准。

## 新增与未定义需求

本文未列出全部产品规则，也不把代码当前行为自动提升为业务决定。
修改现有功能时先检查对应 contracts 覆盖情况及相关实现/测试；缺失的业务含义在本次需求中明确，不从旧阶段记录、Mock 或页面外观推导新规则。
验收结果记录在对应任务或发布证据中，不混入长期规则。新增稳定业务决定时更新对应主题，不复制一套开发指南。
